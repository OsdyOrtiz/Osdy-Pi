# osdy-pi release runbook

## 1. Resolve authority and release identity

- Treat skill activation as instructions, never permission. Obtain explicit human approval for the chosen version and dist-tag; separately obtain grants for source edits, commit, tag, default-branch changes, push, npm publication, and optional GitHub release. Execute only granted actions. Preparation does not imply publication.
- Verify the actual repository root, remote identity, branch, and worktree, and read its release ledger and repository instructions. Confirm the manifest name is exactly `osdy-pi`; do not rely on the folder name or this skill's location. Record the chosen version, approved dist-tag, and intended registry before mutations.
- Inspect tracked, staged, and untracked changes. Identify ownership and coordinate one writer. Preserve unrelated changes byte-for-byte; never reset, clean, stash, stage, or commit them implicitly. If their effect on packaged bytes is uncertain, stop and agree on a clean, separately authorized worktree rather than silently including them.
- Scope this skill to the local project. Do not install it globally, mutate a registry/configuration, or add `.pi` resources to the npm manifest. Authentication configuration belongs to the human, not the skill.
- Use the official registry explicitly for identity, lookup, publication, and verification: `https://registry.npmjs.org/`. Resolve placeholders below into concrete values; never reuse an old version, path, file count, or artifact from a previous run.

## 2. Align version and complete the mandatory README gate

1. Inspect `package.json`, `package-lock.json`, and applicable current-version assertions in tests. Set the approved version consistently in the manifest, lockfile top-level `version`, and lockfile `packages[""].version`; update current-version assertions, not historical fixtures indiscriminately. Preserve other lock entries and unrelated changes; a version-only release does not authorize dependency updates.
2. Review `README.md` against the actual release source and manifest. Updating README before packing is mandatory whenever facts change. Check highlights, shipped features, counts derived from actual resources, exact names, install/update/version instructions, compatibility requirements, and known limitations. Do not advertise unshipped features or turn an unverified behavior into a claim.
3. If there is no factual README delta, record review proof instead of a cosmetic edit: identify the reviewed README revision, compared source/manifest paths, checked sections and facts, and why each remains accurate. A missing review is not a no-change result.
4. Finalize README before the release source commit and before packing. Include its factual changes alongside the behavior/version changes in the authorized commit. Preserve no-change review proof in the release evidence without modifying unrelated files.
5. If README, packaged source, manifest, build inputs/hooks, or packaged release documents change after packing, invalidate that artifact for delivery: finalize the new source commit, rebuild, and repeat every artifact check. Excluded bookkeeping such as `odd/` evidence may be updated without rebuilding only after confirming packaged inputs, inventory, and retained artifact hashes remain unchanged; keep its commit separate and record the original frozen source commit. Do not patch an archive or change an already published version. Changes to published facts/code require a newly approved version.

## 3. Validate and freeze source

- Derive focused tests from affected behavior. Run them first, then the relevant full suite. Current package scripts are `npm test`, `npm run typecheck`, and `npm run lint`; inspect the chosen revision's scripts before execution. Run `git diff --check` and review the release diff and version consistency. Report skipped checks and failing checks; do not describe a failing required check as ready.
- Passive instruction-only changes need structural verification, not a fabricated behavior RED or a real npm publish smoke test. Release authentication and publication are never test substitutes.
- When the runtime's user-owned native-review switch is on, follow only its current provider-issued inspect/consent/binding/capture/acknowledgement contract. Preserve human consent and opaque authority. Do not invent lifecycle commands, invoke raw review lifecycle commands, or treat review approval as a Git/publication grant. When off, do not force a lifecycle.
- Freeze release source in an explicitly authorized immutable commit. Record its full identity and verify that it contains finalized README, version alignment, and intended packaged changes. A tag is optional and separately authorized; verify its target if used. With no commit grant, stop at prepared changes: do not pack mutable source as a verified release.
- Inspect the committed source and package hooks. Stop if packing would generate uncommitted packaged bytes, mutate dependencies, or require unapproved scripts. Agree on how to commit required generated output first; never bypass unexplained hook behavior.

## 4. Build and retain one verified artifact

1. Use a fresh, authorized build workspace from the chosen commit and a fresh output directory outside the repository. Resolve both to concrete absolute paths; retain the output, do not depend on a hardcoded temporary location. Keep unrelated working-tree changes out of the build. Do not install dependencies or create worktrees without the appropriate authorization.
2. Pack only that committed source, using `npm pack --json --pack-destination <absolute-output-directory>`. Derive the actual filename from the returned JSON; resolve and record the concrete absolute `.tgz` path. Do not assume a filename from a version template.
3. Inspect the actual archive independently of pack output. Dynamically enumerate its complete member inventory, sizes, and entry types; compare it to the committed manifest's inclusion rules and automatically included npm files. Reject duplicate members, path traversal, unexpected links, unexpected files, or missing runtime resources. Do not hardcode a file count.
4. For every packaged regular file, map its `package/` member path to the corresponding path in the frozen commit, then compare its extracted bytes to that Git blob. Require exact equality for every file, including README and manifest, and record the checked inventory and count derived from it. Check links/types against the commit explicitly or reject them. A matching manifest version alone is insufficient.
5. Explicitly reject `odd/`, `.pi/`, `.pi-dev/`, `.pi-lens/`, `.codegraph/`, `.atl/`, ignored caches, credentials, local configuration, and unrelated artifacts. Inspect inventory and ignore boundaries together; do not assume `.gitignore` controls npm inclusion. This local skill and its runbook must not be npm-bundled.
6. Compute SHA-1 as lowercase hexadecimal and SHA-512 as SRI (`sha512-` plus base64 digest) from the exact retained archive bytes. Compare both with pack output when available and record both independently computed values. Retain commit, README proof, inventory, hashes, checks, and absolute artifact path as release evidence.
7. Before publication, recheck archive bytes/hashes and frozen source identity. Any packaged-input or build-input change since packing requires rebuilding and reverifying; any artifact mutation invalidates verification. Excluded evidence-only changes follow the bookkeeping exception above and never change the artifact's recorded source commit. Publish only this exact retained `.tgz`, never `.` or a newly generated archive.

## 5. Reconcile registry state and authenticate

- Before any publish attempt, query `npm view osdy-pi@<chosen-version> version dist.shasum dist.integrity --json --registry=https://registry.npmjs.org/` and query `npm view osdy-pi dist-tags --json --registry=https://registry.npmjs.org/`. Distinguish an actual not-found response from authentication, network, or service failures; an unknown state is not permission to publish.
- If the version exists and both hashes match the retained archive, resume verification, not publication. Verify the approved dist-tag too; a wrong tag is a gap requiring separately approved tag correction, never republishing.
- If an existing version has different or unavailable integrity evidence, stop. Investigate provenance; never overwrite it or choose another version without human approval.
- Run `npm whoami --registry=https://registry.npmjs.org/` only in an authorized release session. Confirm that the human-approved identity has package rights. Never read credential stores, `.npmrc` secrets, tokens, or environment secrets into chat/logs.
- On `E401`, stop for human authentication with the official registry. Let the human run login and complete browser authentication in their terminal; after confirmation, rerun identity and registry reconciliation. Do not collect a password, token, or browser session.
- On `EOTP`, hand the exact verified artifact path, approved tag, and registry to the package owner. The owner publishes in an interactive terminal and completes OTP/browser prompts there. Never request, echo, retain, or pass OTPs through agent tools or chat. Reconcile before the owner retries any command.

## 6. Publish only with a grant, then verify

- Require the explicit npm publication grant for this version/tag/artifact. Without it, return prepared evidence and the next human decision; do not publish even when authenticated.
- The authorized public publication command is `npm publish <absolute-verified-tgz-path> --access public --tag <approved-dist-tag> --registry=https://registry.npmjs.org/`. Substitute the retained concrete path and approved tag (`latest` only when approved). For EOTP, the owner runs this command interactively; never add an OTP value to logs or chat.
- Record accepted/processing output as provisional, not registry-verified success. On timeout, uncertain exit, disconnect, or accepted-processing followed by `E404`, query registry state before any retry. Never blindly republish.
- Use a bounded read-only reconciliation window: agree a finite deadline and poll interval, query only the chosen version and dist-tags, and record attempts/results. If propagation remains incomplete at the deadline, stop with pending verification and retained artifact evidence. Do not loop indefinitely or infer failure from one E404.
- Once the version becomes visible, require its version to equal the approved version, its SHA-1 shasum and SHA-512 integrity to equal the retained artifact, and the approved dist-tag to resolve to that version. A mismatch stops completion. Missing fields or network failures remain gaps, not success.
- After verification, optionally create a GitHub release only with its separate grant and verified commit/tag binding. GitHub release creation, push, and tag publication are not implied by npm success.

## 7. Return evidence and next action

Report permission boundaries; chosen version and approved dist-tag; full source commit and optional tag; README delta or explicit no-delta review proof; focused/full tests, typecheck, lint, diff and artifact checks with gaps; dynamic inventory/count; concrete absolute retained archive path; SHA-1 and SHA-512; official registry identity/reconciliation and verification results; optional GitHub outcome; and the next human step. Never output secrets. Label the state precisely: prepared, awaiting authentication/grant, accepted-processing, pending reconciliation, blocked mismatch, or registry-verified.
